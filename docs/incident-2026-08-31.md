# Incident Report — OpenClaw 2026.8.1 Gateway Recovery

**Date:** 2026-08-31  
**Platform:** Linux / systemd user service  
**OpenClaw version:** 2026.8.1  
**Outcome:** Recovered

## Executive summary

After upgrading OpenClaw, the gateway could not remain ready. Initial probes returned connection failures and systemd repeatedly restarted the process until it reached its start limit.

The incident did not have a single root cause. Startup exposed a sequence of blockers. Resolving one allowed OpenClaw to progress far enough to reveal the next one.

The recovery ultimately required:

1. preserving the existing OpenClaw state;
2. reinstalling the systemd user service after correcting unsafe permissions;
3. explicitly assigning a system agent in the multi-agent configuration;
4. updating an official plugin to match the gateway version;
5. migrating each affected agent's legacy session store to SQLite using OpenClaw's supported doctor workflow;
6. resolving a later legacy exec-approvals migration gate that prevented Doctor from reaching additional state migrations;
7. rerunning Doctor offline so workspace setup/attestation state could be migrated and verified in SQLite;
8. validating runtime, connectivity, UI access, and successful agent turns independently.

No configured agent had to be deleted.

## Initial symptoms

```text
Runtime: stopped/failed
Connectivity: ECONNREFUSED
systemd: repeated restart attempts
systemd: start-limit-hit
```

An early journal error was:

```text
Failed detecting Codex app-server thread bindings:
AgentSelectionRequiredError: Multiple agents are configured, but session agent resolution has no explicit owner.

OpenClaw startup migrations did not complete cleanly; refusing to report the gateway ready.
```

The connection refusal was a symptom. The useful evidence was the startup exception explaining why readiness was refused.

## Stage 1 — Preserve state

Create a verified backup before migration work. General pattern:

```bash
cp -a ~/.openclaw ~/.openclaw-backup-YYYY-MM-DD
```

For releases with the backup CLI, a verified archive is preferable before shared-state migration work:

```bash
openclaw backup create --output <private-backup-directory> --verify
```

Adapt the destination and confirm available disk space first. Keep backup archives private.

## Stage 2 — Service installation and permissions

The installed systemd service reflected an older OpenClaw release after the package itself had been upgraded.

For the version tested in this incident, the supported repair path was:

```bash
openclaw gateway install --force
```

The installer initially rejected unsafe permissions. Affected user-owned systemd paths were corrected narrowly rather than recursively:

```bash
chmod go-w ~/.config/systemd ~/.config/systemd/user
chmod go-w ~/.config/systemd/user/openclaw-gateway.service
```

If another specific service backup file is reported, address that file individually.

## Stage 3 — Multi-agent ownership

The configuration contained multiple agents but no explicit ambient/system owner. A valid existing agent was selected explicitly.

Generic pattern:

```bash
openclaw config set agents.defaults.systemAgent.agentId <system-agent-id>
openclaw config get agents.defaults.systemAgent.agentId
```

`<system-agent-id>` is deliberately a placeholder. Select the correct existing agent for your own environment.

## Stage 4 — Official plugin drift

Deep gateway status identified an official plugin mismatch. Sanitized example:

```text
Plugin version drift: 1 active official plugin not on gateway 2026.8.1
- <official-plugin>: <older-version> → expected 2026.8.1
```

In this incident, the affected official plugin was updated through OpenClaw's plugin manager and then verified with the plugin listing. Updating it was necessary but did not by itself recover the gateway.

## Stage 5 — Legacy session migration

After earlier blockers were removed, the journal exposed:

```text
Legacy session store requires migration:
.../agents/<agent-id>/sessions/sessions.json
```

The migration was performed one affected agent at a time:

```bash
openclaw doctor --session-sqlite inspect --session-sqlite-agent <agent-id>
openclaw doctor --session-sqlite dry-run --session-sqlite-agent <agent-id>
openclaw doctor --session-sqlite import --session-sqlite-agent <agent-id>
openclaw doctor --session-sqlite validate --session-sqlite-agent <agent-id>
```

The Gateway was stopped before destructive Session SQLite import operations.

Three configured agents required migration. Sanitized observed results:

| Agent | Legacy sessions imported | Transcript events | Import issues |
|---|---:|---:|---:|
| `agent-primary` | 1 | 33 | 0 |
| `agent-secondary` | 1 | 35 | 0 |
| `agent-specialized` | 1 | 63 | 0 |

The agent labels above are pseudonyms and do not represent the real internal IDs.

After successful import, a later `validate` could report `targets: []` because the active legacy source was no longer present as a migration target. The successful import output and issue count were retained as evidence.

## Stage 6 — Gateway transport recovered, but agent turns still failed

After the earlier startup blockers were removed, the Gateway could become reachable and the control UI could load. That did **not** mean the application was fully recovered.

A selected agent still failed with a sanitized error of the form:

```text
Legacy workspace setup state requires migration for <workspace-path>;
run openclaw doctor --fix.
```

This established an important distinction:

```text
Gateway reachable ≠ every agent runtime is ready
```

## Stage 7 — Exec approvals migration catch-22

The same upgrade also left a retired file-backed approvals source in place. The CLI reported:

```text
Legacy exec approvals exist at ~/.openclaw/exec-approvals.json.
Run `openclaw doctor --fix` before using exec approvals.
```

Safe inspection showed that the legacy JSON was valid and minimal, while the canonical SQLite approvals table existed but did not yet contain the imported document.

Repeated Doctor runs did not retire the legacy source. This matched an upstream `2026.8.1` regression report in which the repair sequence can encounter the approvals migration gate before reaching the migration step that owns the legacy file:

- <https://github.com/openclaw/openclaw/issues/133813>

The recovery preserved the legacy document outside the canonical blocking path and imported it through the public approvals CLI before rerunning Doctor. The preserved source was retained privately as a rollback artifact.

This workaround is **version-specific** and should not be copied blindly to future OpenClaw releases. See [UI Reachable but Agent Turns Fail After Upgrade](ui-agent-runtime-migration.md).

## Stage 8 — Offline workspace migration

With the Gateway stopped and the approvals migration gate cleared, `openclaw doctor --fix` detected additional legacy shared state and completed the workspace migration.

Representative sanitized output:

```text
Legacy state detected:
- Workspace setup and attestations: legacy files -> shared SQLite state

Migrated workspace attestation to SQLite.
Migrated workspace setup state to SQLite.
Verified canonical SQLite workspace setup state.
Removed retired workspace state after verified SQLite import.
```

A related upstream report documents the same class of `2026.8.1` behavior in which workspace setup migrations are deferred until Doctor is run while the Gateway is stopped:

- <https://github.com/openclaw/openclaw/issues/133881>

Doctor also performed additional version-transition housekeeping. Those unrelated changes were treated as separate post-recovery review items rather than assumed to be the cause of the agent failure.

## Stage 9 — Final validation

After the offline migrations completed, deep status showed the expected healthy Gateway indicators:

```text
CLI version: 2026.8.1
Gateway version: 2026.8.1
Runtime: running
Connectivity probe: ok
Listening: loopback:18789
```

The control UI was reachable, and multiple expected agents successfully completed simple test turns.

That final application-level test was necessary. Gateway transport health alone had previously produced a false sense of completion.

## What did not solve the incident alone

Several actions were useful diagnostically but were not complete fixes by themselves:

- quarantining an older plugin-related sidecar artifact;
- running the generic `openclaw doctor --fix` path while the Gateway still owned shared state;
- correcting the plugin version mismatch;
- restarting the gateway before all legacy stores were migrated;
- treating a reachable UI as proof that agent runtime state was healthy;
- repeatedly running Doctor while the legacy approvals gate remained unresolved.

This demonstrated that upgrade recovery can expose multiple sequential blockers across service, configuration, plugin, session, shared-state, and agent-runtime layers.

## Lessons learned

Treat recovery as a stateful diagnostic process:

**backup → inspect → fix one evidenced blocker → probe → fresh evidence → test the actual agent runtime**.

A stronger completion model is:

```text
Gateway process healthy
        ↓
control UI reachable
        ↓
agent runtime/state ready
        ↓
expected agent completes a test turn
        ↓
recovery confirmed
```

Do not delete state simply because a filename appears in an error. When OpenClaw provides a supported migration path, use it and preserve the resulting manifests and backups until recovery is confirmed. If a shipped release contains a repair-path regression, preserve evidence and clearly label any workaround as version-specific.

## Privacy note

Agent IDs, local usernames, session UUIDs, migration-run identifiers, hostnames, infrastructure-specific names, workspace names, approval contents, and other unnecessary environment identifiers have been removed or replaced with placeholders/pseudonyms.
